# 主题22：Skill 设计方法论

## Compiled Truth

**终极验证**：删除一个文件后，功能是否仍然完整？如果不能，说明你在过度设计。

Skill 设计五原则：
1. **代码量最小化**：能用 prompt 解决的不用 scripts
2. **流程扁平化**：避免多层包装，尽量一层完成
3. **格式要求前置**：在 SKILL.md 明确输出格式
4. **复用机制**：参照已验证的模式
5. **Token 效率**：减少不必要的脚本调用和文件 I/O

反模式：❌ 为简单任务添加中间层 ❌ 在定时任务 prompt 重复已有格式要求

## 关键要点

- **Skill 设计五原则**：代码量最小化、流程扁平化、格式要求前置、复用机制、Token效率
- **终极验证**：删除一个文件后功能仍完整 → 不过度设计
- **反模式**：过度设计、重复强制、多层脚本
- **核心洞察**：问题不在脚本数量，而在要求是否明确前置
- **品味即约束**：把审美判断、版式规则、容错逻辑固化成边界

## 📌 每日对话（2026-06-27）

**碰撞：** 卡兹克说「Prompt→Skill→Hook→Loop」层层递进，但你昨天用cron job做daily-session-summary时暴露了一个模糊地带：定时触发的cron+skill，到底算Skill还是Hook？如果用你沉淀的「Skill五原则」自检——「删掉cron job，skill还在吗？删掉skill.md，cron还能跑吗？」——daily-session-summary其实不是一个纯粹的Skill，它是一个Skill和Hook焊在一起的产物。

**纵深：** Unix哲学把"什么时候做"（cron）和"做什么"（脚本）分开，但Hook把二者焊在一起——触发条件成了能力的一部分。这和20年前SOA→微服务的演变同构：编排逻辑从独立层融入了服务本身，导致边界消失。

## 📌 Hook 机制澄清（2026-07-18）

**触发：** 在 Hermes Agent 中实践 lark-cli Hook（C360/会议结果自动截断）时，发现原来的理解有一个关键模糊点——需要把 Hook 和 Skill+Script 在两个维度上彻底切开。

### 核心洞察

Hook 和 Skill+Script 不是同一层的东西。它们的执行权归属完全不同：

```
Skill + Script:    输入 → [LLM] → "我要调这个Script吗？" → 调/跳 → 输出
                                ↑
                         执行权在 LLM
                         LLM 可能跳过，可能不调用
                         结果：不可靠

Hook:              输入 → [Hook Script] → 结果 → [LLM] → 输出
                            ↑                      ↑
                    机器先执行                 LLM只处理精华
                    100% 保证执行
                    结果：可靠
```

### 本质区别

| 维度 | Skill + Script | Hook |
|------|---------------|------|
| **谁决定执行** | LLM（可能跳过） | 框架/机器（100%执行） |
| **执行时机** | LLM 推理之后 | LLM 推理之前 |
| **LLM 感知** | 知道 Script 存在（可决策） | 不知道 Hook 存在（无感知） |
| **适用场景** | 需要 LLM 判断是否有必要 | 确定性的、不需要推理的工作 |
| **类比** | LLM 的"待办清单"（可跳过） | 管道的前置过滤器 |

### 为什么这很重要

**Hook 的本质 = 把不需要推理的确定性工作从 LLM 的"待办清单"里删掉。**

这不是工程师的洁癖，而是有两个实际收益：

1. **省 token**：LLM 不需要看到"要不要做脱敏"这个决策——它拿到的已经是脱敏后的干净数据。每省一个决策 = 省一次推理 token。
2. **保证执行**：Skill+Script 模式下，LLM 可能因为上下文太长、优先级判断失误、或者纯粹"忘了"而跳过 Script。Hook 在框架层强制执行，不存在"跳过"的可能。

### 对 Skill 设计五原则的延伸

原来的五原则（代码量最小化、流程扁平化、格式要求前置、复用、Token效率）覆盖的是「Skill 层」的设计。Hook 补上了「框架层」的视角：

> **新增隐含原则**：确定性工作应该下沉到框架层（Hook），不要让 LLM 承担"要不要做"的决策负担。

这意味着 Skill 设计的边界更清晰了：
- **Hook**：脱敏、格式化、结果截断、模型路由——这些是"应该做且永远该做"的事
- **Skill + Script**：需要 LLM 判断场景是否适用、需要灵活性的事
- **Prompt**：纯文本指令，不涉及代码执行

### 与前文的呼应

6/27 讨论的"cron+skill 模糊了 Hook 与 Skill 的边界"——现在可以精确回答了：

**cron+skill 确实是 Hook 的性质，但实现方式是在 Skill 层**——它借用了 LLM 的推理能力来执行，所以仍然有"LLM 可能跳过"的风险。真正的 Hook（框架层强制执行）应该是一个独立的机制，与 LLM 的推理循环完全解耦。

## 📌 843行实战案例：Hook × 暗知识 × 泊松爆发（2026-07-18）

### 案例背景

客户动态监控 Skill 经过多轮迭代，文件膨胀到 **843 行**。这个"胖"不是设计失误，而是历史积累的必然——每一轮迭代都在叠加 prompt 指令和 scripts，一层包一层，目的是让 LLM 输出更好的结果。

用 Hook 机制让马斯克（aily 智能伙伴）去重构这个 Skill，目标是瘦身到 300-400 行。843 → 300+ 不是删减，而是**把确定性工作从 LLM 层抽走**，让 LLM 不再承担它不该承担的逻辑。

### 关键洞察：坏的更好

> **好案例告诉你这条路通了，坏案例告诉你边界在哪。**

好案例只证明"有一条路能到罗马"。但坏案例——那些曾经踩过的坑、出过的错——才告诉你通往罗马到底有几条路、每条路的边界在哪里。

当 Hook 机制出现时，过去积累的 BadCase（暗知识）不需要重新收集——它们已经在那里了。直接拿来做回归测试，立刻验证新机制是否覆盖了旧问题。

### 三要素合流

```
暗知识（主题7）  =  燃料    →  历史 BadCase 是回归测试的原料
泊松过程（主题26）=  时间律  →  前100次迭代看似无感，实则铺路
Hook 机制        =  火花    →  新机制点燃积累，爆炸式验证
```

这不是"第101次我做对了什么"，而是因为前100次的沉淀让第101次有了验证的弹药。Hook 本身不是魔法——它只是把已经积累好的暗知识和已经迭代到胖的 Skill，重新按正确的分层原则（框架层 vs LLM 层）组织了一遍。

### 推论：越用越好

不断地使用 AI，不断地把真实场景作为原始上下文融入——不管好的坏的。**坏的甚至更好**，因为当新机制或新理解出现时，能立刻验证、立刻迭代。效率远超"新机制 → 配置 → 等待验证"的冷启动路径。
