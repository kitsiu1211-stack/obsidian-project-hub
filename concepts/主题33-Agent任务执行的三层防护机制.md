# 主题33：Agent 任务执行的三层防护机制

## Compiled Truth

Agent 的定时任务（Cron）要"一定跑成功"，不能靠运气，要靠分层防护。这个认知源于一次真实事故：每日认知对话在 9:05 开跑，DeepSeek 600 秒无响应被硬掐断，当天任务直接断掉——早期任务少、并发低，断了说一句"重新看一下"就行；但进入正式生产环境，必须系统化防"断"。

**三层防护结构**：

**第一层：执行层（Agent 跑任务本身）**。任务启动、干活、产出。这一层的问题是：失败那一刻，执行它的 Agent 进程已经死了——被超时掐断的进程不存在"意识到自己失败"的能力。**被监控对象不能监控自己**，人晕倒了没法自己叫醒自己，必须靠外面的人。所以"Agent 自动识别我出问题了然后重跑"在失败瞬间这个层面，架构上做不到。

**第二层：哨兵层（任务后的延迟检查 + 提前退出）**。主任务之后 30~60 分钟安排 1~2 次纯脚本检查（no_agent 模式，零 token）：有成功输出 → 静默收工（你什么都不会收到）；没有输出 → 自动触发补跑 + 发一条提醒。关键设计是"只在需要时花钱"：成功时脚本输出为空 = 完全不消耗 token、零打扰；失败才动用补跑。这是把"自我识别失败"从已死的 Agent 手里，转移到一个永远醒着的观察者手里。

**第三层：备用链（模型调用层兜底）**。主模型卡住时，在还没超时之前框架就自动切到备用模型（如 DeepSeek → MiniMax）重发同一次请求，对话根本不断。它作用在"调用"层而非"任务"层——不让失败发生，而不是等失败再补救。等于你说话对方没听见，旁边的翻译立刻帮你复述一遍。

**够用原则**：三层里执行层 + 哨兵层 + 备用链叠起来，两层防护已经足够。如果连备用链都挂（两个大模型同时出错、脚本也出错），那是机器级故障而非配置层问题，概率少之又少——真出现也没有别的办法，认了。防护的本质是概率管理，不是消灭所有可能性。

**通用性**：这套结构不限于 Cron——任何"Agent 要可靠地完成定时产出"的场景都适用：先跑起来（执行层）→ 低成本观察者盯结果（哨兵层）→ 调用层自动切换兜底（备用链）→ 任务自身幂等（补跑不产生重复副作用）。判断补跑安全性看任务是否有防重复规则（如先查今天是否已产出，已产出就不重写）。

## 关键要点

- **事故起点**：DeepSeek 600 秒超时掐断任务，当天产出断掉 → 逼出系统化防护
- **被监控对象不能监控自己**：失败的 Agent 进程已死，识别失败必须外置给观察者
- **三层结构**：执行层（跑任务）/ 哨兵层（延迟检查+提前退出）/ 备用链（调用层不让失败发生）
- **哨兵核心设计**：纯脚本零 token、成功静默、失败才触发补跑——只在需要时花钱
- **备用链的层次**：作用在调用层而非任务层，切模型重发同一请求，对话不断
- **够用原则**：两层防护足够；双模型同时故障是机器级问题，概率极低，认了
- **通用范式**：跑起来 → 低成本观察者盯结果 → 调用层自动兜底 → 任务自身幂等
- **幂等是补跑的前提**：任务有防重复规则才敢自动重跑，否则补跑产生重复副作用
