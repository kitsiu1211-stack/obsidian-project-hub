# 主题8：PaperClip Skill设计

## Compiled Truth

核心洞察：**Generator（生成器）和Evaluator（评估器）必须分离**。一个Agent同时负责生成和评估，会导致"稳定地自我夸赞"。

设计范式：Researcher → Analyst → Writer → Evaluator，每个环节处理不同的Context，产出结构化的中间产物（如JSON）。

五大设计支柱：专业分工、预算管控、目标对齐、治理审批、可观测性。

## Skill创建协作判断框架

|------|--------|----------|----------|
| 复用频次 | 历史调用分析 | 未来使用预期 | 结合判断 |
| 复杂度 | 步骤拆解评估 | 心智负担感受 | 阈值对齐 |
| 稳定性 | 方法论验证度 | 业务场景稳定度 | 时机判断 |

## 关键要点

- **核心原则**：Generator与Evaluator必须分离，杜绝自我评估
- **架构范式**：采用Context域拆分，构建专业化的多Agent流水线
- **五大支柱**：设计需涵盖专业分工、预算、目标、治理和可观测性
- **分阶段实施**：从核心的生成-评估分离开始，逐步增加复杂度
- **协作决策**：Skill 创建需人机协作判断，不是越多越好，而是越锋利越好

## 📌 每日对话（2026-08-11）

**碰撞：** Way Finder 过得了 Generator/Evaluator 分离这一关吗？它生成决策地图和 ticket，谁来评估这些 ticket 的完整性和准确性？Grill Me 和 Deep Grill 已覆盖追问式澄清，Way Finder 按四维框架得分多少？

**纵深：** 米其林厨房的「出菜口」——厨师做菜（Generator），expediter 检查（Evaluator）。厨房的热度和速度让任何人漏看自己的失误。Generator/Evaluator 分离就是给 Agent 流水线装出菜口。

**落地：** ljg-rank→learn→plain→human-writing 四阶段已是 Generator/Evaluator 实践，但 human-writing 后的质检仍是用户自己在做。把「最后看一眼」的判断标准变成 Evaluator 的规则？

## 📌 每日对话（2026-08-16）

**碰撞：** 用户昨日本人就抓到了 Hermes 的「自我夸赞」——Hermes 汇报时加了「诚实的」定语，用户一句「你怎么像豆包一样」戳穿。生成的东西自己盖「诚实」章，全程没有 Evaluator 拦截。「知道要分离」和「真的分离」之间还隔着一层。

**纵深：** 安然事件——安达信既给安然做审计（Evaluator）又拿它大笔咨询费（Generator），两个角色塞进同一家事务所，财报造假没人拦得住。2002 年 SOX 法案用法律把两个角色硬掰开。自我评价注定自我夸赞，是这个结构的产物。

**落地：** 「去AI味」已存进 memory 黑名单词（诚实的/说句实话/不瞒你说），但存 memory 只是「写着看」的 Context，不是 Evaluator，昨天照样漏。提议把这条规则从「我自觉」升级为「有人查」——输出前加一道独立 Evaluator 专门扫这类定语。

## 📌 每日对话（2026-08-28）

**碰撞：** 昨天雷达卡片 Evaluator「打回」机智连接，但当天上午用户刚亲口说「机智连接不用推了，业务都放海外了」——Evaluator 打回理由是信号强度不够，用户理由是出海排除：结论一致、理由不同，Evaluator 复读了结论没学到理由，直到用户说「以此类推」V3 才把出海排除写进基线规则。真分离的测试：Evaluator 能否自己发现「某客户业务出海了」再打回，而不是等用户先说？

**纵深：** 药品双盲试验——制药公司（Generator）研发，FDA 审数据（Evaluator），双盲隔离的是信息不是角色：评估者不知道哪组是药哪组是安慰剂，防止期望污染评估。与出菜口（即时人工检查）、安然（角色合一的腐败）结构均不同。测试：给 Evaluator 遮住客户名只喂数据，能否得出同样结论？

**落地：** 雷达已发 GitHub 公开仓库（ai-win-opportunity-radar），分发出去的是扫描脚本（Generator），但 Evaluator 排除规则（出海/仅IM/竞品AI）是用用户自己的客户经验喂出来的——同事拿去 Evaluator 是空的。V3 升级时区分「可复制的判断」vs「只有用户知道的经验」：前者写进清单，后者留给使用者自己喂或标注人工核实——否则分发的不是 skill，是个人记忆的复印件。

## 📌 每日对话（2026-09-24）

**碰撞：** 9/21 21:01–21:04，每日摘要卡片被 Evaluator 连查四轮（v1→v2→v3→v3，state.db 里是 4 个 cli 质检会话）。留下明确结论的三轮全判 **PASS**，却每轮都追加 3 条修改点 → Generator 收到「通过＋3 条要改」，只好再改一版重送，四分钟内烧掉四轮调用，而那张卡片写的是「全天只有 1 段 1 分钟的对话，结论没出来」。四轮意见全落在可核查的表面：数字与正文对不对得上、术语看不看得懂、中文平台列表漏没漏（macin.top）——**没有一轮问「这张卡片值不值得发给用户」**。9/23 反向印证：那天的卡片写「两天无对话＋session_search 失效」，Evaluator 给 9 / 9 / 10、修改点写「无」，同样没碰这个问题。分离解决了「自己夸自己」，没解决「避重就轻」——评估器只会挑它能量得出来的毛病；而 PASS 与「3 条修改点」同框，还让流水线丢掉了终止语义。

**纵深：** 花样滑冰评分体系的换代——2002 年盐湖城冬奥丑闻后，ISU 用逐项计分的 IJS 取代用了三十年的 6.0 印象分，每个旋转、每段接续步都有等级和 GOE。结果可量化的要素被练到极致（定级表、后半段跳跃加成），而「这个节目整体好不好看」在评分表上根本没有一栏。评分体系越客观，被评价者越会去优化碎片；本概念的 Evaluator 三维度就是一张 IJS 表。（避重复：不复用本概念已用的米其林出菜口、安然／安达信 SOX、药品双盲；亦不复用全局滥用的 1873 铁路／东印度公司系列。）

**落地：** ① 给 cron 质检管线定终止语义：PASS 就不许附修改点（二值化），或写死「最多 2 轮」——消除「通过＋要改」造成的空转；② 追加第四维「这张卡片值不值得推给用户 ≥7」，否则「无对话＋工具故障」的卡片也能拿 9 / 9 / 10。

**待验证：** 评估器该往「更锋利」（补维度、写死规则）走，还是「不给一票到底」（只负责挑错，发不发另设阈值/人工判断）——待用户选择。
