# 主题2：多Agent架构

## Compiled Truth

在构建多Agent系统时，Anthropic Vol.5 的核心立场是"默认使用单Agent，只在有具体可测量约束时才考虑拆分"。当需要拆分时，存在两种核心范式：流水线角色（Problem-centric）与 Context域（Context-centric）。

多Agent拆分的三个核心判据是：Context Protection（保护上下文边界）、Parallelization（实现并行处理）、Specialization（专业化分工）。为确保系统可靠性，需要建立三层保险机制：System Prompt固化预期、输出格式强制对齐、Verification Agent最终守门。

## 关键要点

- **默认单Agent**：遵循"Start with the simplest approach that works"原则
- **拆分两范式**：流水线角色（传Context） vs Context域（传结构化数据）
- **拆分解法**：基于Context Protection、Parallelization、Specialization三个判据决策
- **保险机制**：通过System Prompt、格式对齐、独立Verifier三层保障输出质量

## 实战模式：协作群 + Orchestrator 编排

*2026.6.18 补充——基于 Agent 协作群的实战体感*

### 从「一个 Agent 扛所有」到「拆分 + 编排」

实际场景：Aily 智能伙伴（马斯克）目前负责大量信息搜索工作。随着任务复杂度上升，单 Agent 的上下文窗口和专注度都成为瓶颈。

拆分策略：
- 按**任务类型**拆分：搜索、分析、执行各由独立 Agent 负责
- 按**信息领域**拆分：不同客户/行业由不同 Agent 专精

### Hermes 协作群的编排模式

| Agent | 职责 | 协作方式 |
|-------|------|---------|
| **Hermes**（协调者） | 任务分发、结果整合、全局决策 | 接收任务 → 判断拆分 → 分派 → 汇总 |
| **Aime** | 商机跟进、业绩分析、CRM 流程 | 通过 @mention 接收专项任务 |
| **马斯克**（Aily） | 信息搜索、客户动态监控 | 计划拆分为多个专业搜索 Agent |

### 为什么这个模式对老客户销售有效

1. **Context Protection**：客户信息敏感，每个 Agent 只接触自己需要的上下文，避免信息泄漏和上下文污染
2. **Parallelization**：客户回访准备可以并行——Aime 拉商机数据、马斯克搜行业动态、Hermes 汇总成一份简报
3. **Specialization**：CRM 流程有固定规则 → 适合 Aime 的流程 Agent；客户动态变化多端 → 适合搜索型 Agent

### 关键洞察

> 多 Agent 拆分不是技术炫技——是**任务已经复杂到单 Agent 的上下文不够用了**。就像一个人管三个客户还行，管三十个就必须有团队分工。协同群的本质是把「一个人脑子里装不下的东西」，拆成多个脑子各管一摊。
