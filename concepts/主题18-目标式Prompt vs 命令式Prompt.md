# 主题18：目标式Prompt vs 命令式Prompt

## Compiled Truth

AI协作的本质区别不在于"给不给指令"，而在于给"微操作指令"还是给"约束+成功标准"。

| 命令式 | 目标式 |
|--------|--------|
| 具体微操作指令 | 约束+成功标准 |
| "加虚线分割线" | "这三段要分割开来，不然容易混淆" |
| 机械执行 | 自主选择最优解 |
| 丑陋、不一致 | 框定范围+视觉层次 |

核心原则：**约束优于指令**——定义边界和成功标准，而非每一步怎么走。

## 关键要点

- **范式迁移**：从"微操作指令"到"约束+目标"的AI协作方式升级
- **Harness映射**：人设计环境（Context），AI自主运行，约束优于指令
- **实践对比**：命令式→机械执行；目标式→自主选择最优解
- **普适应用**：写代码给复杂度要求、做PPT给视觉层级要求、写文案给注意力目标

## 📌 每日对话（2026-08-09）

**碰撞：** Hermes 的 5554-token 全量注入本质是命令式架构——系统不信任 Agent 能自己路由，所以强制把所有 skill 描述塞进上下文。路由表是对这套架构的第一次目标式反抗。但用户自己在给 Agent 下指令时——比如改会议纪要时说「去掉括号、换三条建议」——仍然是命令式。自我指涉：教别人用目标式的人，自己还在用命令式。

**纵深：** 1978 年小岗村大包干——在此之前中国农业是命令式（上级决定种什么），大包干只定「交够国家的，留足集体的，剩下都是自己的」，把决策权还给离土地最近的人。粮食产量三年翻倍。飞书 AI 的 5554 token 注入 = 命令式农业，路由表 = 大包干的第一步。
 
**落地：** 销售场景的映射——命令式销售（列功能：「飞书可以做知识问答、会议纪要……」）vs 目标式销售（问痛点：「你们最想把什么重复性工作先自动化？」）。Lai Sun 那场会 Clement 说「老板只看到最靓那面」——典型命令式销售的后果。如果先问「IT 团队最担心什么」而不是先讲飞书能做什么，信任成本会更低。

## 📌 每日对话（2026-08-15）

**碰撞：** 昨天「云端仓库也要星空」是一句纯目标式指令，Agent 却判断错三次（先当同步、再当视图、最后才查到插件 0.5.0 + Obsidian 憋新版没重启）。目标式是否只在「AI 判断力 ≥ 任务判断需求」时成立——判断力不够时命令式反而更可靠？

**纵深：** 普鲁士「任务式指挥」——老毛奇「与敌人一接触任何计划都失效」，只下达任务+意图，前线临机决断，因战场信息变得比命令传递更快。比大包干狠一步：放权给「离信息最近的人」而非「离土地最近的人」。失效条件：下级不理解意图时任务式比命令式更糟。

**落地：** 四级楼梯本质是回答「目标式/命令式对谁适用」——判断力越弱越靠命令式（带他搭工具），越强越可用目标式（问痛点）。目标式不是普适铁律，是「判断力分布」的函数。

## 📌 每日对话（2026-08-27）

**碰撞：** 昨天「金额阶梯+场景判断器」打法沉淀——「9900快用完→大赛造势」「29.7半年耗尽→消耗曲线测算」，每档触发信号/打法/决策人全写死 = 命令式。教 Agent 用目标式、给团队却自动退回命令式——判断力不对称导致给别人的产出退回命令式。与 8/9 自我指涉成镜像：上次是自己还在用命令式，这次是给别人写命令式。手册到底在帮团队，还是在替团队放弃思考？

**纵深：** 巴黎奥斯曼改造 vs 苏联标准住宅（赫鲁晓夫楼）——奥斯曼不规定每栋楼内部布局，只给约束（统一高度/立面材质/街道宽度），建筑师约束内自由设计→城市和谐又有变化；苏联全国一张图纸、千城一面，盖得快但品质崩坏。约束的密度决定产出是「多样性中的和谐」还是「千篇一律的复制」——不是放不放权，是边界怎么画。

**落地：** 场景判断器已隐含答案：5 信号=约束，6 路径=参考指令。手册拆两层——新人附「照着做的参考打法」（命令式附录），老手只留「触发信号+目标」（目标式骨架）。判断力不同的人吃同一份手册会消化不良。

## 📌 每日对话（2026-09-25）

**碰撞：** 9/18 Claude Code v2.1.277 加入 AGENTS.md 支持，但只在项目内**没有** CLAUDE.md 时才读它——一份被叫作「给 Agent 看的 README」的纯目标式说明文件，能不能生效取决于一条写死的加载优先级。用户 9/20 正好问过这件事的意义。回看 8/27 那版手册：骨架是目标式（触发信号＋目标＋决策人），真正决定团队行为的却是附录里「照着做」那几条。→「约束优于指令」可能缺一个前提：**场上只有一份 context 时才成立**；两份 context 抢同一个 Agent 时，胜负由门控决定，不由优雅决定。

**纵深：** 航空的「适航指令」——航司可以自定 SOP、机长有现场最终处置权，但 FAA／飞机制造商发出适航指令时，机长无权用「我现场判断更优」去盖掉它；指令优先于公司 SOP，也优先于个人经验。多份规则抢同一个执行者的时候，靠的从来不是哪份规则写得更优雅，是一条事先写死的优先级。（避重复：不复用本概念已用的小岗村大包干、普鲁士任务式指挥、奥斯曼 vs 赫鲁晓夫楼；亦避开全局的 1873 铁路、东印度公司、泰勒→德鲁克、集装箱／对数表。）

**落地：** 用户群里的 bot＋路由表本身就是已手动写死的「优先级门控」；客户侧会撞上同一道题——9/20 Tag 培训里王芷伊讲「一个 Tag 要能自己分出来各种群和场景，不是一件事就引入一个 Tag」，翻成客户的话就是「我们已经有 N 个群、N 套流程，撞上了听谁的」。建议在 9/22「确认团队 Tag 开通＋申请演示租户」前把口径备好：不说「Tag 都能懂」，说「撞的时候谁的判断优先，我们可以一起写死」。
