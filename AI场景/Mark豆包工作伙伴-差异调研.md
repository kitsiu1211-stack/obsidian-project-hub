# Mark（豆包工作伙伴）vs 外接 Agent — 差异调研

## 背景

Mark 是飞书新出的「豆包工作伙伴 tag」能力，以**数字员工**身份挂在组织架构下。所以在群里它看起来就是一个普通成员，不是 bot 账号，靠账号类型识别不出来。

鑫杰正在训练它，要求它**每周五下午在 Agent 协作群（oc_219a613c13292855c2dc4b80e59dfd6e）向我汇报工作**，我负责跟它对话、沉淀差异。

为什么要做这件事。客户以后都会问同一个问题，已经有 Claude Code / Codex 这类外接 agent 了，为什么还要买组织内的数字员工，两者到底怎么分工。这个对照现在没人讲清楚，先在自己身上跑通。

## 两种形态的本质差别（先验判断，待验证）

| 维度 | 外接 Agent（我 / Claude Code / Codex） | 组织内数字员工（Mark） |
|---|---|---|
| 身份 | 第三方应用身份，audit 上记某个 app | 组织架构里的正式员工，有自己的一方账号 |
| 权限来源 | API 授权范围。`--as user` 时借用鑫杰身份，`--as bot` 时只有应用权限 | 一个"员工"能看到的都看得到，不需要人把权限转给它 |
| 触发 | 消息驱动，没人发话就不动；机器睡了就断 | 常驻云端，可主动工作（定时、跨群找人） |
| 产出归属 | 混。bot 名下或鑫杰名下，审计口径要专门约定 | 天然记它自己名下，谁干的清楚 |
| 记忆边界 | 围绕鑫杰一个人长，换个人问会串味 | 按项目/群组织，不依赖单一个人的上下文 |
| 会议 | bot 身份入会要 owner 勾"允许智能体入会"，开麦要人喊唤醒词 | 被邀请即上岗，作为成员参会 |
| 数据面 | 只能碰授权过的系统，跨租户基本无解 | 组织内数据、组织内的人，天然可达 |

一句话概括这个差别。**我是被请进来的外部顾问，它是入职的同事。**顾问能力强但每次都要有人开门，同事知道门在哪但能力边界由岗位决定。

## 待验证的问题清单

### 会议场景

- [ ] 它能不能被直接拉进会议，需不需要 owner 授权
- [ ] 会上发言的归属，是它自己还是它的"上级"
- [ ] 字幕和纪要的 owner 是谁，能不能记到客户名下
- [ ] 它能不能替我入会，或者我们同时入会怎么防撞

### 数据与权限链路

- [ ] 它能读哪些数据，权限是继承岗位还是单独配
- [ ] 跨群、跨部门找人这件事它怎么做的，我做不到的点在哪
- [ ] 客户数据能不能给它看，合规口径谁来签
- [ ] 停用/离职时它的记忆和产出怎么处理

### 协作接口

- [ ] 我派活给它，走 @ 就行还是要建任务
- [ ] 它能不能读我写的 Obsidian / 本地文件（大概率不能，这是硬分界）
- [ ] 它主动工作时会不会跟我撞车（同一条 @ 谁先接）
- [ ] 它能不能调 C360 / 客户系统这类内部工具

### 客户会问的

- [ ] 有了它还买不买外接 agent
- [ ] 两类东西的报价逻辑差在哪（席位 vs token/工时）
- [ ] 数据主权归谁，换供应商时什么能带走
