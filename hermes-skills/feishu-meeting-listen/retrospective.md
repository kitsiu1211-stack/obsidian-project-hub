## 根因分析

### 错误 1：每次升级都是重写，不是增强

V3 的核心能力：
- poll.sh 捕获字幕 → JSONL
- 会议结束 → Agent 读 JSONL → 生成纪要
- 会后自动执行待办

这个链路是对的。但从 V4 开始，每次「升级」都丢弃了上一个版本的全部逻辑，从头写。结果：
- V4/V5：bash poll 方案折腾 5 版，从未稳定
- V6：Python 方案丢掉了纪要生成能力，只剩 C360 推送

**教训：新版本必须包含旧版本的全部功能，只增不减。**

### 错误 2：过早自动化

V3 是手动激活（「监听会议」），V4 开始追求全自动（launchd 守护、cron 轮询）。

自动化本身没问题，但：
- 自动化需要不同的架构（事件驱动 vs 轮询驱动）
- 在没有验证手动流程稳定之前，不要自动化
- 自动化引入了新问题（超时、竞争条件、多实例）而没解决旧问题

**教训：先跑稳手动，再考虑自动化。**

### 错误 3：过度工程化

V6 拆成 2 个 cron job + LLM 每 3 分钟轮询，凭空消耗 token。

V3 的简洁方案：Agent 收到「监听会议」指令 → 启动 poll.sh → 等待退出 → 生成纪要。零额外 token。

**教训：简单方案能用就别加复杂度。**

### 错误 4：丢失上下文

每次修改时，我只看了当前代码，没有追溯 V3 的完整工作流。poll.sh 和 SKILL.md 还在文件系统里，但我没有参考它们，直接重写。

**教训：改动前先读历史版本，搞清楚什么是对的。**

### 错误 5：用户反馈被忽视

用户多次说「V3 已经能实现需求了」「V4/V5 没一次成功」，但我还是继续在错误的架构上修补。

**教训：用户说「回退」时，不要试图修复，直接回退。**

## 幸存的能力（V3 核心功能）

1. ✅ poll.sh — 旁听捕获字幕到 JSONL
2. ✅ meeting_detect.py — 零 token 静默检测 + 自动启动 poll.sh
3. ✅ Agent 手动激活模式 — 用户说「监听会议」→ Agent 接管

## 当前架构（2026-07-16 最终版）

```
meeting_detect.py (cron, 零token, deliver=local)
  └─ 静默检测入会 → 自动启动 poll.sh

用户说「监听会议」
  └─ Agent 检查状态 → 确认监听中
      ├─ 客户会议 → C360 查商机+跟进 → 推卡片
      └─ 会议结束 → 读 JSONL → 出纪要 → 会后执行
```

## 升级铁律

3. **手动流程跑稳至少 3 场会议后，再考虑自动化**
4. **用户说「回退」→ 立即回退，不修补**
